# دفاعیه فنی: امکان‌سنجی پایپ‌لاین OCR پروژه documentocr

**تاریخ:** 2026-11-14
**دامنه:** فقط پایپ‌لاین خود پروژه (Surya + PaddleOCR) — EasyOCR صرفاً به‌عنوان مبنای مقایسه، نه موتور محصول.
**وضعیت سند:** پیش‌نویس قابل دفاع (evidence-based) — موارد «نامعلوم» صریحاً علامت‌گذاری شده‌اند.

---

## ۱) خلاصه اجرایی

پروژه از نظر **تولید داده (Konkour)** سالم و قابل اجراست. گلوگاه اصلی، **لایهٔ خواندن متن (recognition)** است:

- **Surya** موتور اصلیِ خواندن متن پروژه است و نسخهٔ نصب‌شده (2.5) **آخرین نسخهٔ موجود** است؛ اما مدل recognition آن **به‌صورت لوکال موجود نیست** و یک‌بار دانلود ~۰.۸۴GB لازم دارد.
- **PaddleOCR** فقط برای layout/detection به‌کار می‌رود و **مدل‌هایش لوکال هستند**، ولی **رانتایم paddlepaddle ناسازگار** است (2.6.2 در برابر نیاز 3.x) و روی این ماشین کرش می‌کند.
- **راه‌حل قابل دفاع:** مسیر **Surya-only** با بک‌اند **llama.cpp** — که تصویر داکر آن **از قبل روی همین ماشین موجود است** — همراه با یک دانلود یک‌بارهٔ مدل Q8 و حفظ Paddle فقط به‌عنوان قابلیت اختیاری/degraded.

**نتیجه امکان‌سنجی:** ✅ **شدنی با ریسک پایین** برای Surya-only؛ ⚠️ **ریسک بالا و ارزش کم** برای احیای Paddle.

1. **اجرای کامل و آفلاین** هر دو ورک‌فلو (تولید کنکور + OCR عمومی) بدون وابستگی به سرویس خارجی.

- حجم دقیق wheel GPU پدل روی PyPI موجود نیست — **Unknown**.
- دسترسی به بانک سوالات کنکور واقعی وجود ندارد — **blocked خارجی**.

## ۷) جمع‌بندی دفاعیه

1. **وضع موجود:** تولید کنکور ✅، تشخیص خط ✅، خواندن متن ❌ (مدل نیست)، Paddle ❌ (رانتایم ناسازگار).
2. **مسیر رسیدن به مطلوب:** یک دانلود یک‌بارهٔ ۰.۸۴GB + استفاده از داکر llama.cpp موجود + اتصال Surya؛ بدون نیاز به تغییر نسخهٔ Surya (2.5 آخرین است).
3. **پیشنهاد قابل دفاع:** **گزینه A (Surya-only با llama.cpp)**؛ Paddle به وضعیت «اختیاری» تنزل یابد تا ریسک کرش از مسیر اصلی حذف شود.
4. **دلیل رد گزینه C:** دو شکست ثبت‌شده روی همین سخت‌افزار و ارزش پایین (Paddle فقط layout می‌دهد، نه خواندن متن).
5. **دلیل رد گزینه D به‌عنوان موتور:** EasyOCR متعلق به پروژه نیست؛ فقط به‌عنوان baseline مقایسه‌ای نگه داشته شود.
